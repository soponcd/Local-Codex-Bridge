# UI 意图确认流程

先确定用户要完成什么、在什么环境使用什么产品形态，再确认信息组织与核心行为；技术栈、组件和视觉表达随后确定。本流程用于有 UI 的新增或变更需求，不是通用审批系统，也不代替业务数据、权限和业务验收。

## 执行顺序与交互

主控负责展示明确问题和当前产物、收集用户决定；执行者负责调查、结构化记录、实现和证据。蓝图不充分时先交互补齐，不把 Agent 推测写成用户决定。已有有效确认可引用原始记录及适用版本，不要求用户重复确认未变化的内容；一次用户回复可明确确认多个节点，但不能默认为全链批准。

```text
目标蓝图 → 使用环境与产品形态 → 同层需求单元
                              ↓
                    App/模块结构树 + 核心动态流程
                              ↓
                    技术栈 + 模板差异复用
                              ↓
                    信息表达 + 真实 UI → 用户 UI 验收
                                          ↓
                              真实业务验收（现有业务门，可交接另一任务）
```

每个节点输出版本、输入来源和待确认问题；在展示后记录用户原文引用、确认对象和摘要。程序检查声明结构与摘要，不认证用户身份，不替用户判断方案。不得把 Agent 自评、主控裁决实现质量或测试 PASS 记作用户确认。合成 fixture 仅验证程序路径。

| 节点 | 输入 | 操作与用户需决定事项 | 输出 | 放行条件 | 变更失效范围 |
| --- | --- | --- | --- | --- | --- |
| blueprint | 用户目标、既有蓝图与真实来源 | 补齐目标用户、问题、结果、边界、关键业务对象；用户确认做什么、暂不做什么 | 目标蓝图、结果判据、明确未知项 | 关键目标与范围有适用用户确认；无关键未知阻止后续判断 | 本节点及所有下游 |
| environment | 蓝图、设备/场景/渠道、已有产品形态 | 调查移动/桌面/浏览器、联网离线、输入方式、平台权限、部署约束；用户确定使用环境与产品形态 | 环境与产品形态约束、已有栈适配依据 | 使用环境与产品形态均已确认，影响选栈的关键约束无未决；不预设Web，不靠组件库反推产品 | environment及下游 |
| requirements | 蓝图、环境、业务对象/输入输出 | 在同一层、同一分类标准下列 MECE 需求单元，补遗漏、消重复；再按用途聚合模块，允许明确跨模块共享对象 | 需求ID、用途、输入输出、结果判据、模块映射 | 用户确认需求覆盖和聚合用途；每项可追溯到蓝图 | requirements及下游 |
| architecture | 需求映射、既有模式目录与本页候选目录 | 分别选择App级和模块级组织模式；同时展示结构树与核心动态流程，解释跨模块关系、异常与返回路径 | App/模块信息架构、结构树、核心流程、模式选择理由 | 用户共同确认结构与流程；流程含入口、状态、关键决定、完成/失败/取消/返回，不以多个视觉近似demo代替 | architecture及下游 |
| stack | 已确认环境/形态/架构、现有技术栈、find-wheel记录 | 优先复用现有产品栈；比较组件或模板，明确可复用部分、差异、改造量与三阶段成本 | 技术栈及模板差异方案、来源与版本、find-wheel绑定 | 用户确认有实质取舍的技术方案；构建前现有find-wheel门有效；默认不是Web | stack及下游 |
| expression | 已确认组织与行为、平台规范、可访问性要求 | 设计层级、密度、排版、色彩、控件与状态表达；到真实UI阶段才用适用UI技能 | 可运行真实UI、状态覆盖、版本与实际页面/窗口证据 | 用户确认表达方向；实际实现与结构/流程一致，未确认实景明确待验收 | expression及下游 |
| ui_acceptance | 当前真实UI、结构/流程、针对性检查、已知限制 | 在实际目标环境展示并走核心场景；用户确认该版本UI可接受或给出修订 | 用户UI验收记录、范围、版本、未验证项 | 有当前版本的用户验收；编译/单测/截图存在均不能自动通过 | 本节点；若反馈改变上游，则从实际变化节点失效 |
| business_acceptance | 有来源且适用的真实业务输入、目标判据、实际代码/配置版本、业务结果证据 | 按项目现有业务验收门核对输入及计算/执行口径；负责业务验收的人确认结果和范围，可交接另一任务 | 版本绑定的业务验收结果、证据、未验证范围和交接位置 | 现有业务门实际通过；UI验收和合成测试不替代业务结果；不要求与UI同一任务完成 | 变化的业务输入/判据/版本及受影响结果重新验证；反馈改动UI时回到相关UI节点 |

失效不是删除历史：保留旧产物和确认来源，将变化节点及依赖它的下游标为需更新。任务revision变化先核查适用性，不表示全链用户重审；未变化的节点可以引用原确认并记录仍适用的依据。普通无关进度不触发重审。组件实现细节变化而架构与表达不变，仅重新核验受影响实现和UI版本。runtime保守地隔离revision，不自动判断语义不变；显式重登记未变化内容后，用ui-decide的source_revision与applicability重新绑定已登记原证据。不同摘要、来源被修改、原决定非confirm均不得复用。重新绑定是执行者的适用性声明，不是新用户确认；变化节点仍需用户确认。

business_acceptance仅为现有业务门的交接节点，runtime不新增业务审批、身份或完成状态；UI任务可交付UI验收范围并标明业务验收待另一任务完成。

## UI四层原则

这是用户于2026-09-27批准的AGILite开发原则，不声称已定位或引用ESD原文。四层是实现职责，不是四个审批阶段；不强制四目录/四文件、不强制Web、不新增依赖、runtime schema或门禁。小组件可同文件组织，已有产品只按本次差异应用。

| 层 | 职责与产物 | 边界 |
| --- | --- | --- |
| Tokens | 可复用且有设计含义的色彩、字体/字距、尺寸/间距、圆角、阴影、动效等，使用统一来源的语义token；记录语义名、来源和适用主题/平台，例如surface、text-muted、space-content、motion-feedback | 可引用基础值或平台语义资源；业务参数、密钥、运行数据不属于UI token。不强制全部数字token化，一次性局部值说明用途即可，不为合规制造无意义token |
| Structure | 页面骨架、区域、导航、语义与a11y、组件组合；产物是区域/组件树及导航和可访问性关系 | 不塞复杂请求、业务逻辑或散落样式值；结构允许简短事件绑定，委托行为职责，不强求零事件或零平台布局声明 |
| Presentation | 布局、样式、状态视觉、响应式和主题；产物是表达/状态方案与tokens消费关系 | 消费统一tokens，不维护第二套散落的设计值真源；不承担复杂业务状态转换与请求编排。平台声明式语法可与结构相邻，但职责应可辨认 |
| Behavior | 事件、状态转换、校验、异步反馈、取消与恢复；产物是核心事件/状态路径及服务边界 | 业务服务调用经明确接口边界，组件不堆整套业务实现；业务规则、认证与数据真源留在业务服务/领域职责中，不因四层拆分复制状态 |

依赖关系：Structure组合区域和组件并绑定简短动作；Presentation消费Tokens并按状态表达；Behavior管理交互状态并经边界调用业务服务；同一状态真源驱动结构与表现，不从样式反推业务完成。信息组织模式仍按用途选择，视觉风格不是信息架构。

| 平台 | 允许的职责映射（候选，不强制目录） |
| --- | --- |
| React | 语义JSX与组件组合；CSS/样式系统和主题消费语义tokens；handler、hook或已有状态模型承担Behavior，服务接口承接业务调用；简短onClick等绑定可留在JSX |
| Vue | template与组件/slot组合；style与主题消费tokens；script/composable或已有状态模型承担Behavior，服务接口承接业务调用；SFC同文件合法，简短事件绑定可留在template |
| SwiftUI/原生 | View组合、导航与accessibility承担Structure；系统语义颜色/字体、资源、布局和modifier承担Presentation并引用token来源；State/Binding/Observable或现有模型承担Behavior，经服务协议调用业务；不为分层舍弃原生控件或强迁移栈 |

在现有节点中执行，不新增节点或必填runtime字段：

- architecture/stack：结构树与核心流程仍共同确认；在既有技术方案的selection_basis/reuse_delta说明中记录四层职责映射、token来源、状态真源、服务边界和复用差异。无需再生成四份模板或让用户分别批准四层。
- expression：在既有presentation/states/artifacts说明中给出实际组件/样式/行为路径、token引用与主题/响应式/a11y状态覆盖；保留取消、失败、恢复和异步反馈的实际证据，不仅展示静态视觉。
- ui_acceptance：按当前code_commit和目标环境，针对性检查有设计含义的复用值能追溯统一token来源，结构不混入复杂请求/业务实现，表现消费tokens且各状态可辨认，行为校验/异步/取消/恢复经服务边界。按适用平台核查键盘/焦点/读屏、主题与响应式；不适用项记依据，缺失证据保留未验证。该检查不替代用户UI确认或业务验收。

## 可复用的信息组织模式目录

先找目标项目已经使用的模式目录、导航和对象模型；有效则引用并增量适配。本表是紧凑候选，不是强行 MECE 的产品分类、唯一架构或默认UI模板。应先写用途和选择依据，再选择模式；“Apple风格”“卡片风格”“深色”属于表达，不能说明信息如何组织。

### App级候选

| 模式 | 适用目的 | 选择依据与典型结构 | 组合规则与易错点 |
| --- | --- | --- | --- |
| 文档型 | 创建、编辑、管理持久文档或项目 | 用户围绕文档工作；文档库→文档工作区→内容/工具/版本 | 工作区可嵌树、编辑器与检查面板；不把文档状态混成全局导航 |
| 知识库型 | 按主题浏览、检索、定位和复用知识 | 用户以找信息为主；分类/集合→搜索结果→内容/来源 | 分类与检索是同一知识的不同入口，保留统一对象ID、过滤条件和返回位置 |
| 流程任务型 | 完成有状态与交接的任务 | 用户关注下一步和结果；任务库/队列→任务详情→阶段动作/结果 | 模块可用步骤流程、看板或详情面板；状态是业务真源，不用按钮颜色推断完成 |
| 对话接待型 | 通过会话接收意图、澄清与交付结果 | 用户以对话为主要入口；会话库→消息流→上下文/产物 | 对话与任务/知识模块可组合；明确建议、草稿、执行和结果，不能把模拟回复画成业务交付 |
| 监控控制型 | 观察系统并对明确对象采取动作 | 用户关注当前状态、告警、趋势、控制对象；概览→对象/告警详情→授权控制 | 显示更新时间、未知/失败；控制与只读指标分开，状态图不能替代动作确认 |
| 对象工作台型 | 在多个对象间高效查找、比较、编辑 | 用户围绕实体操作；对象集合→选择→详情/编辑/关联 | 可作为上面模式的模块，也可承担App主结构；避免每个模块重复维护同一实体 |

### 模块级候选

| 模式 | 适用目的与选择依据 | 与App级组合规则 |
| --- | --- | --- |
| 列表/表格→详情 | 对象多，需搜索、排序、比较或查看详情 | 集合是入口、详情引用同一对象；保持选择、过滤和返回上下文 |
| 树/目录→内容 | 层级关系本身帮助定位文档、知识或配置 | 树表达真实层级；交叉关系用标签/关联，不复制多个冲突树 |
| 消息流+上下文/产物 | 按时间对话，随消息追溯引用和生成结果 | 对话流不承担全部导航；上下文与产物保留身份、来源和生命周期 |
| 步骤流程/向导 | 有明确前置条件、输入校验与阶段顺序 | 与任务对象绑定；显示保存、失败、取消、返回和重试，不要求无必要的线性步骤 |
| 看板/状态队列 | 按状态分组任务并识别下一步 | 状态移动对应真实业务转换；自由拖动不能绕过状态规则 |
| 概览→下钻 | 先发现异常，再定位对象和证据 | 汇总口径与时间窗可见，下钻保持过滤口径；未知不能画成零或正常 |
| 编辑器+检查面板 | 内容创作、配置、即时校验或预览 | 草稿与保存版本分开；检查面板辅助当前对象，不制造第二份真源 |
| 时间线/日历 | 时序、期限、依赖或历史决定任务安排 | 与对象列表互为视图；区分计划、实际与推断时间，不重建独立对象库 |

选择记录最少写：主用途、用户关键动作、核心对象及状态、App主模式、各模块模式、未选方案的具体原因。组合采用一个清楚的App主导航、多个按用途匹配的模块模式；共享对象和跨模块流程通过ID与明确入口连接，避免重复导航和状态。App级与模块级可以不同，不用全App同一种版式证明一致性。

结构树需列全局入口、模块、子区、核心对象和关联；动态流程需标角色、触发、输入、状态转换、失败/取消、结果以及跨模块跳转。先用两者检查覆盖与一致性，再讨论表达风格。模块聚合可多用途；MECE要求用于同层需求拆分，不强加于以上模式候选。

## 例外与证据边界

- 无UI项目或本次只改非UI逻辑：显式记录原因、适用范围，不生成虚假UI确认。后续新增UI需重新判断。
- 已有产品和技术栈：引用已有有效蓝图/结构/确认，仅处理本次差异；除非目标环境或必要能力不匹配，不迁移栈或要求旧项目重复初始化。
- 技术原型可以验证平台能力，但标为探索；不能拿多个类似demo替代结构与流程确认。
- 用户UI验收只覆盖该UI及版本，不代表真实业务、生产数据、权限、安全或部署完成。
- 程序门仅约束经TaskStore入口的记录与动作；语义完整性、MECE质量、来源是否确为用户由主控结合原始对话核查，不能声明系统级强制或认证。

## CLI与持久状态

三个命令均使用现有TaskStore与JSON输入，不新建账本。先ui-status读取state_digest；ui-record保存节点content，ui-decide保存用户决定文件的artifact引用。写入需expected_revision、expected_ui_digest；ready阶段无需attempt，running/revise必须传原始attempt_id/owner/epoch。相同content重记为no-op；内容改变清除当前投影中该节点及下游，事件历史保留。draft可逐步整理，但expression要求stack及上游确认、ui_acceptance要求expression确认；显式required任务submit要求UI验收，未配置历史任务保持原有行为。

```sh
agilite_cli ui-status --input /absolute/task.json
agilite_cli ui-record --input /absolute/node.json
agilite_cli ui-decide --input /absolute/decision-binding.json
```

task.json含task_id。node.json含task_id、stage、content、上述revision/state摘要及适用attempt fence。每节点content键见runtime的FIELDS，与上表输出对应。environment.constraints使用对象含unresolved:[]，有影响选栈的未决项先澄清。requirements.units是含id/purpose/input/output/criterion的列表；module_mapping是模块用途到需求ID列表，每项有唯一主归属，交叉关联另记。

decision-binding.json包含task_id、stage、content_digest、evidence:{path,sha256,size}及上述fence。被引用JSON消息记录包含task_id、revision、stage、content_digest、role:"user"、kind:"user_message"、decision:"confirm|revise|reject"、text、source_ref。text引用实际用户原文，source_ref精确定位原消息；一次多节点确认须分别指明对象。Agent不能自行编消息；登记只是来源声明，宿主真实性仍需核查。测试使用kind:"synthetic"，投影为simulated且不放行实现或UI验收。旧原证据复用另加source_revision、applicability；不修改原消息字节。读回重新核验确认和UI产物artifact；变更/缺失变为stale。UI状态不是task完成状态。

初始化安装单份 `.agilite/ui-workflow.md`、runtime与入口；已安装副本升级继续使用自己的该文件，不依赖源仓库路径。已有项目仅在明确升级时变更托管产物，schema仍为3；无需迁移数据库或重走旧项目初始化。未提交实现不能进入要求clean commit的TaskStore check/submit，直接本地测试须明示candidate与未正式验收。

防绕过边界：已配置任务的新revision没有scope时仍为pending，不当作未配置。普通ui-record禁止required降no_ui；范围确变更时先change-goal并重绑轮子，再以scope_change_evidence引用当前revision的真实用户scope确认，且新revision尚未声明scope。UI验收content须有当前干净代码完整code_commit；提交核对该版本并冻结ui_binding，后续_result重验状态与全部投影证据。代码变化须更新验收版本；证据丢失/漂移不可用旧提交继续review/集成/完成。

曾声明required的来源要求保留在事件历史中，即使后来no_ui也不能清除。no_ui同摘要重记保留并核验原scope_change_evidence；reason等内容摘要变化或跨revision须重绑适用于新摘要/revision的有效真实用户范围证据。丢失来源后改reason不能恢复放行。
