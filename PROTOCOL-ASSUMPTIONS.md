# Native Codex App-Server Protocol Assumptions

**Status:** Current local engineering baseline, including accepted native History / Goal / lineage / Queue / Search behavior and installed `codex-cli 0.158.0-alpha.2.1` schema qualification. Revalidate this checklist whenever the native Codex runtime is upgraded. This is an upgrade aid, not a complete app-server protocol reference.

LCB remains a thin supervisory MCP adapter. The native Codex thread/session is the sole execution source of truth; Bridge state must not become a second task system, model-state registry, or lifecycle authority.

## MCP result compatibility

The current Bridge returns every successful tool result in `structuredContent`, with only a tiny text marker in `content`. Callers must stop parsing success JSON from text content. Errors retain the explicit `isError` / text error path. `codex_threads(include_turns:true)` is rejected with migration guidance to `codex_history`; observe after runtime loss remains metadata-only, and resume uses `excludeTurns:true`.

## Native Goal qualification

Installed `0.158.0-alpha.2.1` exposes `thread/goal/set|get|clear` in ordinary and experimental schemas. Set accepts `threadId` plus optional nullable `objective`, `status`, and `tokenBudget`; get returns a nullable goal, clear returns `cleared:boolean`. Native owns goal validation, lifecycle and usage accounting. Objective length is delegated to native to avoid a competing JavaScript character-count rule. Positive safe-integer input bounds and safe-integer checks on native accounting fields protect transport precision.

The public Bridge set contract requires an explicit `budget_mode` before any native mutation: preserve omits `tokenBudget`, unlimited sends null, fixed requires a positive safe-integer `token_budget`. Preserve/unlimited reject the amount field; no mode or budget default exists. This gate applies only to Goal set, not Turn, Queue or Steer.

Native preflight verified that budget omission preserves the value and explicit null removes it, that unloaded-thread goal calls need no resume, and that paused goals survive both loaded resume and a fresh process's cold resume. Subsequent independent MCP/Bridge qualification preserved an active goal through the existing resume/turn-start path; clearing it left the same turn active, and that turn completed normally. A native resume probe also observed automatic continuation, including a turn-start notification arriving after a clear acknowledgement: clearing a goal is not a barrier against already-scheduled execution and is not turn interruption. Requalify these version-specific lifecycle observations on upgrades; nonzero usage preservation/reset and in-progress pause remain unqualified.

`codex_goal` forwards one request and preserves eligible native response bodies and additive fields. Required identity/envelope/accounting checks, the existing sanitizer, and a 256 KiB result-body bound gate success; a rejected delivery explicitly retains the native success acknowledgement. This differs from an already-sent set/clear acknowledgement timeout, whose outcome is UNKNOWN. No automatic resume, goal reconstruction, retry, compensation, or checkpoint write is added. Goal notifications retain the existing waking diagnostic passthrough and raw replay paths.

Revalidation surfaces: `src/goal.ts`, `src/tools.ts`, `src/app-server.ts`; goal, MCP and acknowledgement-timeout tests. Watch nullable/omission meanings, native statuses, required numeric fields, precision and response size, new execution side effects, and notification shapes on upgrades.

## Native capability / lineage qualification

Fresh ordinary and experimental TypeScript exports from installed `0.158.0-alpha.2.1` retain native `sessionId`, `forkedFromId`, `parentThreadId`, source and agent fields. `canAcceptDirectInput:boolean|null` and the `thread/list` parent/ancestor filters are experimental-only in these exports; Bridge already opts into experimentalApi. Capability null is unavailable, not false; absent older fields stay absent. Read these as native response facts, never a cross-client writer lease, permission cache, or Bridge turn-input gate.

`codex_threads` maps optional nullable `parent_thread_id` / `ancestor_thread_id` / `source_kinds` to native `parentThreadId` / `ancestorThreadId` / `sourceKinds`. Only two non-null lineage filters conflict. Source kinds use the installed ten-value vocabulary; omission, null and [] keep native interactive-source defaults. The 100-entry input-array ceiling is a transport bound. There is no implicit subagent expansion, client-side descendant traversal, retry, read-to-resume, or new state store. Parent/ancestor filters describe spawned descendants, not fork lineage. The [official App Server reference](https://learn.chatgpt.com/docs/app-server#list-threads-with-pagination--filters) corroborates native filtering; installed schemas and live evidence govern version-specific behavior.

Read-only qualification on an existing dedicated stored thread preserved lineage values and capability null through direct native read, MCP metadata read and observe fallback. Native loaded/list remained empty. Native accepted parent/ancestor, explicit null and [] combinations, and rejected two non-null lineage filters. This project had no matching stored spawned-thread sample in the bounded lookup: nonempty descendants, loaded capability true/false and older absent fields have deterministic coverage, not live qualification. No native thread/turn was created or resumed. Existing metadata sanitizer limits still apply; this is not a new whole-response lossless guarantee.

Revalidate `src/tools.ts` and `test/lineage.test.ts` on schema changes, especially capability availability, source defaults, null/filter exclusivity, fork-vs-spawn scope and opaque pagination. Errors propagate without broader fallback queries.

## Native Queue qualification

Installed `0.158.0-alpha.2.1` exposes `thread/queue/list|add|update|delete|reorder` in experimental TypeScript exports only; Bridge already opts into experimentalApi. Native also exposes `thread/queue/start`, but this Bridge surface does not call or expose it. Direct-native and separate MCP/Bridge live qualification both observed active A followed automatically by queued B and C, all completed; CRUD, full reorder and single-page cursor continuation were exercised while A was active. These are installed-runtime observations, not a durable upstream scheduling guarantee.

Each `codex_queue` action makes one native request. Add passes caller-supplied `clientUserMessageId`; update/delete/reorder use native submission IDs. Add/update write one text UserInput with empty text_elements; update replaces the entire input array. List preserves eligible non-text and additive fields. Native owns queue membership, permutation validity, consumption races and execution. No implicit resume/start, queue store, scheduler, merge, retry, compensation or checkpoint update is added. Caller IDs are not assumed to guarantee idempotency.

List requests one page (default 20, maximum 100); native cursor/null remains authoritative. Input and response bounds are transport limits, not native queue-capacity limits. Required response envelopes/identities, existing sanitization and a 256 KiB result-body ceiling gate lossless success. `queue_result_not_deliverable:` retains native success acknowledgement, including acknowledged mutation for add/update/delete/reorder; already-sent acknowledgement timeouts remain UNKNOWN. In either case, inspect native queue and execution state before deciding on another mutation.

Native queue-change notifications remain waking diagnostic passthrough facts and raw events. Actual live raw notifications were also replayed through compact, with matching queue-change counts; deterministic MCP/JSONL tests cover both views and all five operations. Cold readback confirmed completed turn history and an empty queue without reconstructing Bridge live state. Queue survival across restart, idle/cold execution, concurrent clients, duplicate-client-ID idempotency and macOS live behavior remain unqualified. Deleting pending input is not turn interruption.

Revalidate `src/queue.ts`, `src/tools.ts`, `src/app-server.ts` and queue/MCP/timeout tests against fresh installed schemas and live behavior on upgrades. The public App Server reference did not document these queue methods at qualification time; the official remote-workflow Queue/Steer distinction corroborates product intent only, not this version-specific API contract.

## Native Search qualification

Installed `0.158.0-alpha.2.1` exposes `thread/search` and `thread/searchOccurrences`. `codex_search(kind:"threads")` maps one native page with exact query, source/archived filters and optional native sort/cursor; no cwd/parent/ancestor filter is implied. `kind:"occurrences"` requires one paginated thread and searches visible user/final-assistant message substrings in native chronological order. Native owns matching, indexing, legacy rejection and cursor validity.

Occurrence `turnCursor` is an inclusive native history anchor for `codex_history(kind:"turns")` on the same thread, not a search continuation. `snippetMatchRange` uses UTF-16 code units with an exclusive end. Eligible pages and additive fields remain unchanged; required envelope/identity/range validation, existing sanitizer policy and a 256 KiB result-body bound reject the whole result as `search_result_not_deliverable:` without partial data/cursor or fallback reads.

Existing Windows native and independent MCP qualification verified locator → narrow history read; deterministic tests cover pagination, exact query/filter forwarding, offsets, malformed/redacted/oversized results and no live-state reconstruction. Multi-thread multi-page, archived/subagent/legacy live coverage and macOS live remain unqualified. Revalidate `src/search.ts`, `src/tools.ts`, search and MCP tests on upgrades; there is no Bridge index, relevance scoring, implicit resume or full-history fallback.

## Compact projection qualification

Compact policies and structural descriptors are qualified against `codex-cli 0.158.0-alpha.2.1` experimental output: 85 notification methods and 19 ThreadItem types. Routing inspects the original notification before transport truncation, then retains only a bounded, redacted projection in the existing event ring. Unknown methods, item types, or incompatible known shapes wake with bounded diagnostic evidence; raw retains its existing sanitized replay semantics.

`account/gatewayOAuth/changed` remains in installed method and shape coverage. Its JSON shape requires string `providerId` and native status (`notReady`, `started`, `succeeded`, `failed`); `authUrl` and `error` are optional-nullable strings in JSON and required-nullable in TS. Valid shapes use `ignore_compact`: no compact fact, activity, or semantic wake, while raw events and cursors remain available. Missing/invalid required fields and unknown status values use the existing `unknown + wake` route. The current notification union contains 83 JSON methods plus 2 TS-only raw methods.

`npm run check:compact-schema` uses the executable selected by `CODEX_EXE` to generate fresh schemas without starting a native session. It compares JSON structural descriptors and TypeScript method/item coverage. It does not fingerprint the transitive TypeScript dependency graph or prove TS/JSON field equivalence. For example, `rawResponse/completed` usage fields are required-nullable in generated TS but optional-nullable in standalone JSON; compact follows the JSON shape. On upgrades, review TS-only field changes where they affect supervision semantics, alongside this check and the relevant runtime tests.

## Revalidation triggers

Revisit this checklist when:

- the official Codex executable or app-server protocol is upgraded;
- any listed method changes request, response, pagination, id, scope, or timeout semantics;
- a required-envelope or protocol-identity check begins failing against native Codex;
- the related model, response, timeout, duplicate-id, or version-anchor tests change or fail;
- Bridge proposes support for a currently deliberate non-assumption.

## Deliberate non-assumptions

- No `serviceTier` or provider-capability abstraction.
- No current-model registry, model cache, or model-state reconstruction from `thread/read`.
- No dependency on `command/exec`. Native `sourceKinds` is used only as an explicitly requested thread-list filter.
- No elicitation response support.
- No Bridge-owned queue or scheduler; native queue management is separate from `turn/steer`, which remains a semantic correction to one active turn.
- No new late-response telemetry contract or public surface was added by the V2.1.3 maintenance round.
